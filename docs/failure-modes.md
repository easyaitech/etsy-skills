# 失败模式命名注册表

本仓反复出现的失败模式命名登记（#120）。目的：PR 描述、code review、CHANGELOG 可以**按名引用**（如「这是又一次复述失真」），不用每次重新叙述根因。每条 = 一句定义 / 实例（带版本锚，均在 CHANGELOG）/ 根因 / 对策。新增条目要求：至少一次真实发生 + 已有明确对策，不收推测性的模式。

## 1. 硬编码断言盲区（hardcoded-assertion blind spot）

- **定义**：把可推导的事实（版本号、话术、枚举）硬编码在校验 / 文档里，改了真源忘了改副本，且没有 CI 会跑到它。
- **实例**：v1.0.11 发版漏改 `validate-listing-read-contract.py` 里的硬编码版本断言，main 上该校验一直 FAIL 却无人发现——当时仓库没有任何 CI；v1.0.15 补记此事并建立 CI。
- **根因**：「每次发版记得改 X」这类人工步骤迟早会漏；没有强制执行的检查等于没有检查。
- **对策**：能机器推导的绝不硬编码（版本号从 CHANGELOG 顶部推导、封存话术从 §封存协议提取）；校验脚本挂 CI 强制跑（v1.0.15 建 `validate` workflow，v1.0.37 增挂 frontmatter 机检器）。

## 2. 手写汇总矩阵腐化（summary-matrix rot）

- **定义**：手工维护的汇总表（跨 skill 总览、速查矩阵）随本体演进而失真，且没人知道它失真了。
- **实例**：v1.0.37 删除 `dependency-protocol.md` 里 11×10 的「基座文件降级速查」——已 stale 缺 5 列，还与各 skill 自有依赖表构成双真源。
- **根因**：汇总表的维护成本随行 × 列增长，review 时没人逐格核对；双真源必然漂移。
- **对策**：汇总一律按需生成不落盘（`scripts/deps-overview.py` 读 frontmatter）；真源唯一化，其余位置只引用。

## 3. 复述失真（restatement distortion）

- **定义**：同一协议 / 话术在多处全文复述，改了一处漏其余，措辞渐行渐远。
- **实例**：v1.0.38 前封存协议在多个文件全文复述、统一话术有两处截断（缺「，请等后续版本」），小红书解封验收清单双副本并行维护；v1.0.36 前各 skill 的 layer 自报口径不一。
- **根因**：复述时每个作者都会微调措辞；没有机器比对就没有漂移信号。
- **对策**：单一真源 + 其余位置引用（CONTEXT.md §真源）；字节级关键话术上机检⑤指纹白名单（`scripts/validate-frontmatter.py`）。

## 4. 触发词蒸发（trigger-word evaporation）

- **定义**：精简 skill 的 frontmatter `description` 时，把「用户原话触发词」当成了可删细节一起删掉，路由从此匹配不到。
- **实例**：v1.0.39 description 瘦身初版删掉了「这单寄到哪 / 买家叫什么」等地址类问句、「自动发这几条」、内容类型 × 平台清单——Hermes 靠这些字面短语路由 skill。
- **根因**：把「写给路由看的信号」和「写给人看的说明」混在一起删。
- **对策**：description 口径 = 身份一句 + 触发词 + 路由边界（机检④限长）；改 description 的 review 专查触发词存活。

## 5. 文案腔调漂移（voice drift）

- **定义**：产出文案在无 sanctioned 模板时可自由发挥的空白处，长年累积出跑偏的固定腔调。
- **实例**：v1.0.32 复盘 25 条已发 pin：十余条全长成 `The Meaning of {汉字} ({拼音})` 博客书名腔（含义检索零命中）、hashtag 多数全缺——旧版只有礼物意图模板，含义型 pin 没有 sanctioned 格式正是自创腔的根因。
- **根因**：没有模板的意图族，模型会发明一个；发明物会自我强化。
- **对策**：给每个真实意图族配 sanctioned 模板（双意图族）+ 前置硬规则（前 40 / 前 60 字符）+ 带真实失守反例的自检清单。

## 6. 不可靠观测回写死循环（unreliable-observation write-back loop）

- **定义**：用不可靠的观测源自动回写数据，覆盖掉店主手工修正，次日再报同样的差异，循环往复。
- **实例**：v1.0.35 材质列退场——公开读腿的材质观测不可靠（Apify 会丢项），造成「店主同步 → 后台回写覆盖 → 次日再报」死循环。
- **根因**：把「多数时候对」的观测当成事实真源去自动覆盖人工修正。
- **对策**：观测不可靠的列整体退场（不比对、不回写）；需要人工与自动并存时，人工修正优先于自动回写。
