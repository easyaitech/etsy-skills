# Inventory（实物库存：成品 + 包材）

这个 skill 管店里**真实存在的东西还剩多少**，核心是店铺总 Base 内的两张表：

| Base | 表 | 管什么 |
|---|---|---|
| `{店铺名}-运营中枢` | `Inventory 库存品` | 一行 = 一个库存单位：成品（真实 SKU）或包材附件（麻布袋 / 小礼品 / 贺卡）；当前库存、安全库存、绑定规则 |
| `{店铺名}-运营中枢` | `Inventory Ledger 库存流水` | 一行 = 一次库存变动：采购入库（+）、销售扣减（-，系统自动写）、盘点调整（±） |

**对外的实操接口**：店铺总 Base 内这两张表（养个店长 Hermes 飞书直聊 runtime 走后端 `POST /api/hermes/bitable/record-list` / `record-create` / `record-upsert`，访问约定见 `../shared/backend-api-access.md`；完整 Codex / Lark 环境用 `lark-base` skill）。

> 共享引导（版本检查 / 工作区解析 / 客户偏好 / 写入约束 / 工作语言 / 经营原则）见 [`shared/preamble.md`](../shared/preamble.md)，降级协议见 [`shared/dependency-protocol.md`](../shared/dependency-protocol.md)。

## 这套系统的三条底层事实（答任何库存问题前必须先认清）

1. **流水是唯一事实源，「当前库存」只是快照**。`当前库存` = 库存流水表里该库存品所有 `变动数量` 之和，由系统算完回写。它是**服务端专列**，通用写工具拒收（返回 `BITABLE_FIELD_SERVER_GENERATED`）——**这不是后端故障**，是设计如此。想改库存，只能往流水表记一行。
2. **商品表的「库存」列不是实物库存**。`Products 商品` 表的「库存」列是 Etsy 平台上的在售挂牌数量（由 listing 读取自动回写），跟仓库里有几个成品没有关系。店主问"还剩多少 / 够不够发"时**绝不能去读那一列**，一律读 `Inventory 库存品`。同理，商品表的 `SKU` 只是店内前端标识，实物库存的身份是库存品表的 `库存品名称`。
3. **销售扣减由系统自动做，你不要手工扣**。新订单首次入库时，后端按绑定规则自动往流水表写「销售扣减」负数行（幂等键 `订单号:库存品名称`，同一单绝不重复扣）。你只负责入库、盘点和配置。

## 依赖关系

| 来源 | 提供什么 | 怎么用 |
|---|---|---|
| `Inventory 库存品` 表 | 库存品清单、当前库存、安全库存、绑定规则 | 一切库存问答的唯一数据源 |
| `Inventory Ledger 库存流水` 表 | 每一次变动的原始记账 | 对账、追溯"这批为什么少了"、记入库与盘点 |
| `Products 商品` 表（listing-catalog） | 商品的 `SKU` / `平台商品 ID` / `品类` | 配绑定时用来确认绑定键写什么；**不提供实物库存** |
| `Orders 订单` 表（orders-customers） | 订单商品行 | 系统自动扣减的输入；人工核对"这单扣了什么"时对照流水的「关联订单号」 |

两张表不存在时（老租户没开通），如实告诉店主"这个店还没开库存管理"，请管理员跑一次库存表开通，**不要自己建表**（表结构由后端 provision 维护，手工建的表列名对不上会让自动扣减失效）。

## 四种执行模式

### 模式 A：查库存（还剩多少 / 够不够）

**进入条件**：
- 店主问某个东西还剩多少（"麻布袋还有几个"、"SCROLL-24x36 还有货吗"）
- 店主问整体库存情况、要一份清单

**执行步骤**：
1. 整表读：`POST /api/hermes/bitable/record-list`，body 带 `logicalTable=accessories`（不带 `fieldName`/`value` 就是整表枚举；问总数只能这样问，过滤出来的条数不是总数）
2. 按 `库存品名称` 找到目标行，读 `当前库存` / `安全库存` / `单位`
3. 回答时把结论放前面（"麻布袋还剩 18 个，安全线 20，该补了"），需要追溯再读流水表（`logicalTable=accessory_ledger`）
4. 表里没有这个名字时**不要猜**：如实说库存品表里没有这一项，问店主是不是叫别的名字、或者要不要现在建一个

**滞后不是 bug**：`当前库存` 由系统在「订单自动扣减后」和「每天早报」两个时点重算回写。店主刚手工记完入库流水，那一列可能还没刷新——这时以流水求和为准，并如实说明"入库已记上，汇总数字最迟明早刷新"，**不要报成写入失败、也不要去手改那一列**。

### 模式 B：记入库 / 盘点（往流水表加一行）

**进入条件**：
- 店主说到货了、采购了多少、补了多少货
- 店主盘点完说实际有多少、说数字对不上要修正

**执行步骤**：
1. 先确认三件事，缺哪件问哪件，**绝不自己编**：哪个库存品（要与库存品表的 `库存品名称` 一字不差）、数量、是入库还是盘点
2. 盘点要先读当前库存算差额：流水记的是**变动量不是结果值**。店主说"实际数了是 30"、系统里是 25，那就记 `+5` 而不是 `30`；备注里写清"盘点：实际 30"
3. `POST /api/hermes/bitable/record-create`，`logicalTable=accessory_ledger`，fields：
   - `库存品名称`：与库存品表一字不差
   - `变动数量`：JSON 数字（入库为正 `100`，盘点差额可为负 `-3`）
   - `类型`：只能填 `采购入库` / `盘点调整` / `其他`（`销售扣减` 是系统专用，你不能写）
   - `备注`：写清缘由（"2026-08-15 到货 100 个"、"盘点：实际 30"）
   - `流水 ID` / `关联订单号`：**一律留空**（服务端自动扣减专用，写了会被拒）
   - `发生时间`：留空，或传毫秒时间戳；**绝不要填日期文本**（日期列收到文本整行被拒）
4. 落库成功后回执说明改了哪张表、加了哪一行、库存从多少变成多少

**流水只追加，绝不修改**：记错了就再记一条冲正（比如多记了 100 就记 `-100`，备注写"冲正上一条误记"），**永远不要 `record-update` / `record-upsert` 已有流水行**——那是篡改账本，会让历史对不上。

### 模式 C：建库存品 / 配绑定 / 设安全库存

**进入条件**：
- 店主要把一个新东西纳入库存管理（新包材、新成品）
- 店主要改安全库存、采购链接，或说"这个商品要配什么包材"

**执行步骤**：
1. 先整表读一眼已有行怎么填的，照抄那套写法（命名风格、单位写法）
2. `POST /api/hermes/bitable/record-upsert`，`logicalTable=accessories`、`keyValue=<库存品名称>`，fields 按需填：
   - `库存品名称`：**成品填真实 SKU**（如 `SCROLL-24x36`），**包材填名称**（如 `麻布袋-小号`）
   - `类型`：`成品` / `包材` / `赠品` / `其他`（只影响筛选查看）
   - `安全库存`：跌到这个数（含）早报点名；留空 = 不提醒
   - `单位`、`采购链接`、`备注`
   - 绑定两列见下
3. 新建的库存品**期初库存要单独记一条流水**（模式 B），不然它一开始是 0
4. 字段语义拿不准查 [`references/base-schema.md`](references/base-schema.md)

**绑定规则怎么配**（决定订单成交时自动扣什么）：

| 列 | 适合谁 | 怎么填 | 效果 |
|---|---|---|---|
| `适用品类` | 包材（整类共用） | 商品表「品类」列里的词，多个用逗号 / 顿号分隔（`卷轴、挂画`） | 该品类的商品每卖一件自动扣 1 个；**以后上新同品类商品零操作** |
| `适用商品 SKU` | 成品（一品一库存） | 商品表的 `SKU` **或** `平台商品 ID`（两个键都认），多个用逗号分隔 | 精确点名，只扣这个商品 |

配之前先去 `Products 商品` 表确认品类词 / SKU 的真实写法（品类词对不上就永远扣不到）。两列可以同时填，命中任意一条即扣。

### 模式 D：补货清单 / 预警

**进入条件**：
- 店主问该补什么货、哪些快没了
- 店主追问早报里的补货提醒

**执行步骤**：
1. 整表读 `logicalTable=accessories`
2. 挑出 `当前库存 <= 安全库存` 的行（安全库存为空的不算），按库存从少到多排
3. 输出：名称、剩余量、安全线、采购链接。有采购链接就带上，店主点开就能下单
4. **库存为负数**说明账目有问题（漏记入库或记反了），必须单独点出来请店主盘点修正，不要混在普通补货里

早报每天会自动点名跌破安全线的库存品，这里是店主主动问时的同一口径；两边都以流水求和为准。

## 写入前的硬性约束

通用约束见 [`shared/preamble.md`](../shared/preamble.md) §写入前的通用约束，**Base 写穿不变量**见 [`../shared/store-base-architecture.md`](../shared/store-base-architecture.md)（改动没真正写进 Base 不算完成，落库与确认同 turn 收口，写完带回执含飞书链接）。本 skill 特有禁区：

- **绝不写 `当前库存` 和 `流水 ID` 两列**：服务端专列，通用写工具一律拒收（`BITABLE_FIELD_SERVER_GENERATED`）。被拒是预期行为，不是故障，改用流水记账
- **绝不改已有流水行**：流水是只追加的账本，纠错用冲正行
- **绝不写 `类型 = 销售扣减`**：那是订单自动扣减的专用值，人工记账只能用 `采购入库` / `盘点调整` / `其他`
- **绝不拿 `Products 商品` 表的「库存」列回答实物库存问题**，也不要为了"对齐"去手改它——那一列是平台在售数量，由 listing 读取维护
- **绝不自己建这两张表**：结构由后端 provision 维护，手工建的列名对不上会让自动扣减静默失效；没有表就请管理员开通
- 数量一律传 JSON 数字，不带单位和符号；库存品名称必须与库存品表一字不差（差一个空格就是另一个库存品，历史流水会对不上）
